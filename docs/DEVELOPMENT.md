# Устройство проекта

## Компоненты

- `app/dashboard.tsx`: ввод, история, подключения, пример и проверка перед отправкой.
- `app/api`: Next.js route handlers, тот же origin, cookie-сессия.
- `lib/domain.ts`: валидация счетов, счётчиков и показаний, периоды Бишкек.
- `lib/auth.mjs`, `lib/config.mjs`: scrypt, подписанные cookie, проверка runtime-конфигурации.
- `lib/gas-adapter.ts`: один POST после получения публичного ключа официального клиента. Ключ не сохраняется в репозитории или логах.
- `lib/water-adapter.ts`: проверяемые функции формата данных/ответа; отправка не подключена.
- `lib/submission.ts`: атомарное резервирование попытки, запись результата.
- `db`: Drizzle SQLite schema, `sqlite-proxy` поверх встроенного `node:sqlite` Node 24. Запросы используют связанные параметры.
- `drizzle`: SQL-миграции; `scripts/migrate.mjs` применяет их транзакционно и проверяет checksum уже применённых файлов.

Один фиксированный владелец `owner` определяется только валидной сессией. Заголовки прежнего хостинга и переданный клиентом owner игнорируются. Приложение не предназначено для регистрации нескольких пользователей.

## HTTP API

| Метод и путь            | Назначение                                                                   |
| ----------------------- | ---------------------------------------------------------------------------- |
| `POST /api/auth/login`  | `{username,password}`; устанавливает cookie                                  |
| `POST /api/auth/logout` | Очищает cookie текущего браузера                                             |
| `GET /api/health`       | `{status:"ok"}`; без персональных данных                                     |
| `GET /api/state`        | Счета и показания текущего владельца                                         |
| `POST /api/accounts`    | `{provider,account,meters:[{id,kind,label,previous}]}`                       |
| `POST /api/readings`    | `{provider,period:"YYYY-MM",values:{meterId:"value"}}`                       |
| `POST /api/submit`      | `{id,version,confirmed:true}`; version = поле `created` выбранного черновика |
| `GET /api/export`       | JSON-выгрузка данных владельца                                               |

Все операции изменения требуют `Origin: <APP_URL>` и `Content-Type: application/json`. Кроме входа и healthcheck, требуется cookie. Тело JSON ограничено 20 КБ. API не является публичным API для сторонних сайтов; CORS не включён.

## Состояния отправки

`draft`, `blocked` или `rejected` могут атомарно перейти в `sending`. SQL проверяет владельца, id, версию и предыдущее состояние. Только победитель условного UPDATE выполняет сетевой запрос.

- `confirmed`: получен ожидаемый подтверждающий ответ поставщика.
- `rejected`: явный отказ поставщика; можно исправить черновик и подтвердить снова.
- `blocked`: сетевой POST ещё не выполнялся, например, не удалось получить публичный ключ клиента.
- `unknown`: POST мог быть принят, но надёжного ответа нет. Повтор и редактирование заблокированы.
- `sending`: процесс мог прерваться после резервирования; запись тоже остаётся заблокированной.

Для `sending`/`unknown` нет кнопки «повторить» и автоматического сброса. Сначала нужна проверка у поставщика. Ручную корректировку базы следует делать только после подтверждения фактического результата. Уникальный ключ `(owner, provider, period)` исключает второй месячный черновик даже при изменении лицевого счёта.

Это предотвращает автоматическое дублирование внутри одной актуальной базы, но не даёт распределённой гарантии exactly-once: сам поставщик не предоставляет проверенный idempotency key, а восстановление старого бэкапа может потерять информацию о последних отправках.

## Тесты

`npm test` запускает Node test runner:

- Правила чисел, периодов, видов счётчиков и ведущих нулей.
- Формат запросов/ответов адаптеров, ошибки, таймауты и отсутствие повторов. Внешний HTTP замокан.
- Настоящие route handlers + Drizzle + SQLite + реальные миграции; проверка атомарной конкуренции, переходов статусов, версии и блокировки неподключённых провайдеров.
- Вход, подпись/истечение cookie, подмена заголовков, CSRF и ограничение попыток.
- Повторное применение миграций, отказ при изменённой миграции, целостный WAL-бэкап.

После `npm run build` команда `npm run test:smoke` проверяет настоящий standalone HTTP-сервер с временной SQLite, затем перезапускает сервер и проверяет сохранённые значения. CI дополнительно делает эти проверки внутри Docker с read-only rootfs, непривилегированным пользователем, постоянным volume и штатным entrypoint.

Тесты не используют настоящие лицевые счета, не совершают платежи и не отправляют тестовые показания поставщикам. Для первого реального отправления газа нужен собственный счёт и ручная сверка результата на официальном сайте.

## Миграции

Измените `db/schema.ts`, выполните `npm run db:generate`, проверьте новый SQL и добавьте его в Git. Уже применённые SQL-файлы не редактируйте. `npm run db:migrate` применяет новые миграции; Docker и `npm start` выполняют это до запуска сервера. Перед обновлением делайте бэкап. Автоматического rollback миграций нет.

## Ограничения первой версии

- Один экземпляр, одно домохозяйство, один лицевой счёт каждого поставщика.
- Нет автоматического получения показаний физического счётчика и планировщика отправки.
- Нет автоматического восстановления неизвестных результатов и импорта JSON.
- Для воды нужен разрешённый официальный доступ; для теплосети не подтверждён контракт отправки; для света сначала требуется уточнить тип счётчика/АСКУЭ.
- Состояние лимита входа хранится в процессе; смена ключа сессий — способ глобального отзыва cookie.
